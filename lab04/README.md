Проверено на Python 3.14.0, OC: Windows 10 Pro, терминал: PowerShell, IDE: Visual Studio Code.

cd lab04
python range_numbers.py
python statistics.py
python positive_input.py
python variant.py

Если команда `python` не найдена, используйте `py` вместо `python`.

## Вариант 11: числа с модулем не больше 3

Условие отбора: `abs(value) <= 3`. Подходят `-3`, `-2`, `-1`, `0`, `1`, `2`, `3`.

Ручной расчёт контрольного набора `-12, -3, 0, 2, 10, 15, 20` до запуска:

| Число | `abs(x) <= 3` | Количество после | Сумма после |
|---|---|---|---|
| `-12` | нет | 0 | 0 |
| `-3` | да | 1 | -3 |
| `0` | да | 2 | -3 |
| `2` | да | 3 | -1 |
| `10` | нет | 3 | -1 |
| `15` | нет | 3 | -1 |
| `20` | нет | 3 | -1 |

Итог: количество `3`, сумма `-1`. При `n = 0` цикл не выполняется ни разу,
поэтому оба результата остаются нулевыми; для набора без подходящих чисел
(`5, 10, -7`) результаты тоже `0` и `0`.

## Накопитель: сумма чисел от 1 до 4

| Итерация | `number` | `total` до | `total` после |
|---|---|---|---|
| 1 | 1 | 0 | 1 |
| 2 | 2 | 1 | 3 |
| 3 | 3 | 3 | 6 |
| 4 | 4 | 6 | 10 |

После цикла `total` равно `10`. Накопитель обнуляется до цикла, а счётчик
положительных значений в `statistics.py` устроен так же: `0`, затем `+1`
на каждом подходящем числе.

## Объяснения

**Почему циклы завершаются.** В `range_numbers.py` и `statistics.py` цикл
`for` идёт по `range`, а количество итераций там конечно и известно заранее.
В `variant.py` число итераций равно `n`, при `n = 0` не выполняется ни одной.
В `positive_input.py` условие `number <= 0` рано или поздно станет ложным,
потому что пользователь вводит новое значение, а программа гарантирует, что
положительное число будет введено. В `prime.py` делитель каждую итерацию
увеличивается на 1, поэтому рано или поздно `divisor * divisor > n`; кроме
того, при найденном делителе цикл завершает `break`. В `statistics.py` нет
риска зацикливания: `range(2, n + 1)` при `n = 1` пуст, и цикл не выполняется.

**Почему `range(a, b)` не всегда подходит для задания 1.** Во-первых, правый
конец в `range` не включается: `range(2, 4)` даёт `2, 3`, а не `2, 3, 4`,
поэтому нужен `range(a, b + 1)`. Во-вторых, шаг по умолчанию положительный,
и при `a > b` такой `range` пуст: для убывания нужен `range(a, b - 1, -1)`.
В-третьих, при `a == b` нужен ровно один вывод, а не особый случай с пустым
диапазоном. Поэтому в программе две ветви, а границы сдвинуты на единицу.

**Почему максимум инициализируется первым числом.** Если начать с нуля, то
для набора `-5, -2, -8` максимум остался бы `0`, хотя такого числа во вводе
нет. Первое значение уже принадлежит набору и служит корректной начальной
точкой; остальные сравниваются с ним.

**Дополнительно: проверка простоты.** Перебор идёт до `divisor * divisor <= n`,
поэтому проверяется порядка `sqrt(n)` делителей, а не `n`. Числа `2` и `17`
дали `Простое`, `9`, `49` и `4` — `Составное`. Рекурсивная запись того же
перебора не делает алгоритм логарифмическим: количество проверок остаётся
пропорциональным `sqrt(n)`, рекурсия меняет только форму записи.
