## Формат данных

`todos.json` — JSON-массив объектов. Каждая запись содержит `id`, `userId`, `title`, `completed`; дополнительные ключи допустимы.

`validate_todos(data)` проверяет:

- корень — список, каждая запись — словарь;
- `id` и `userId` — **положительные целые** (`type(value) is int`, чтобы не принять `True`);
- `title` — непустая строка (проверка после `strip()`);
- `completed` — логическое значение (`type(value) is bool`, строку `"false"` не принимаем);
- `id` уникален.

При нарушении выбрасывается `ValueError` с номером записи.

## Анализ и результаты

- `completion_counts(todos)` — числа завершённых задач для **всех** пользователей, включая тех, у кого ноль.
- `top_users(counts)` — отсортированный список лидеров; `[]` для пустого словаря и при максимуме `0`.
- `leader_tasks(todos, leaders)` — завершённые задачи лидеров в исходном порядке.
- `select_tasks(todos, user_id, parameter=None)` — вариант 11.
- Идентификаторы пользователей сравнимаются как числа; в строки они не преобразуются.

### Индивидуальный вариант 11

Завершённые задачи указанного пользователя, у которых `id` **строго больше** неотрицательного целого порога. Порядок записей сохраняется, исходные записи не изменяются; для неизвестного пользователя — `[]`.

При `user_id=5`, `порог=2` у пользователя 5 задачи `id=1` (выполнена), `id=2` (не выполнена), `id=5` (выполнена) → результат `[5]`.

### Ручная проверка сохранности результатов

1. Запустить `python main.py` с вводом `5` и `2` — создаются `leaders.json` и `selected.json`.
2. Временно заменить `todos.json` на `{"id": 1}` (объект вместо списка).
3. Снова запустить `python main.py` (ввод тот же). Программа печатает:
   `Ошибка структуры данных: Корень данных должен быть списком. Результаты не изменены.`
4. Убедиться, что оба файла результатов остались прежними, вернуть `todos.json`.

**Результат:** файлы результатов не изменились. Причины: чтение и `validate_todos()` выполняются до записи, а `json.JSONDecodeError` и `UnicodeError` (наследники `ValueError`) перехватываются отдельно до общего `ValueError`.

## HTTP: управляемое упражнение

**Адрес.** Запрос идёт на `https://api.github.com/users/<логин>` — это **профиль пользователя по логину**, а не данные репозитория (для репозитория нужны были бы владелец и имя, другой ресурс API). `quote(login, safe="")` экранирует логин для использования в URL. Внешние библиотеки и токен не нужны.

**GET.** Метод GET читает ресурс и не изменяет его — для получения профиля этого достаточно. Статус `200` означает успех; `404` — пользователь не найден; `403`/`429` — ограничения доступа или частоты запросов.

**Таймаут.** `urlopen(request, timeout=10)` ограничивает ожидание ответа 10 секундами: без таймаута программа могла бы зависнуть при недоступной сети.

**Заголовки.** `Accept: application/vnd.github+json` задаёт нужный формат ответа, `User-Agent` — обязателен для запросов к GitHub API.

**Обработчики ошибок** (порядок важен): `HTTPError` ловится раньше `URLError`, так как является его наследником, и показывает код ответа; `URLError`, `TimeoutError` и `socket.timeout` означают сетевую проблему; `ValueError`/`UnicodeError` — неверный логин, испорченный JSON или ответ непохожий на профиль; `OSError` — ошибка записи файла.

**Результат упражнения.** Выполнен один запрос для `octocat`: ответ получен (`HTTP 200`), профиль сохранён в `profile.json` (логин `octocat`, имя `The Octocat`). Поля со значением `null` не заменялись выдуманными данными — в файл записан исходный ответ API. Проверять изменяемые поля на совпадение с чужим примером не требуется.

**Дополнительное задание.** В `fetch_profile.py` добавлено консольное меню: `1` — сеть, `2` — локальный пример. Оба источника проходят через общую функцию `check_profile()` (проверка структуры) и общую функцию вывода `show_profile()`. Локальный режим проверен: прочитан `profile_sample.json`, выведен логин `demo`, имя `None` (исходное `null` из файла). Сообщение «Использованы учебные локальные данные» явно указывает, что применены локальные данные.
